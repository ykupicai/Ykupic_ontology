# 備援打同一台主機，就不是備援

## 問題

「大量圖資轉換工具」取周邊地籍改走空間查詢後，把原本的逐筆查詢路徑保留為 fallback，
理由寫得很順：「農業部服務會間歇性斷線（2026-08-19 某評估案實踩 WinError 10060），
斷線時自動改走舊路徑」。程式照這個說法寫了自動切換，訊息也照這個說法印。

精簡程式碼時順手查了兩條路的實際位址：

```
主路徑（空間查詢）  https://coagis.colife.org.tw/.../CadastralMap_Tiled_<版次>/MapServer
fallback（逐筆）    https://coagis.colife.org.tw/.../CadastralMap/SOE/MapServer/exts/CoaRESTSOE/...
```

**同一台主機、同一份 token、同一個設定檔。** 該站一斷，兩條路一起斷。

## 原因

寫 fallback 時想的是「**換一種做法**」（範圍查詢 vs 逐筆查詢），
沒有往下追「**這兩種做法最後打到哪裡**」。兩者在程式碼裡看起來距離很遠
（不同模組、不同參數、不同解析邏輯），在網路上卻是同一個網域、同一台伺服器。

危險的不是這條 fallback 沒用，而是**它宣稱能擋的事情它擋不住**——
錯誤訊息會告訴操作的人「已改走備援」，讓人以為問題已被處理。

## 解法

1. **把 fallback 真正能救的情境寫清楚，不要寫它救不了的那個。**
   本例改寫成：救不了全站斷線；真正能救的是「Tiled 服務單獨不可用而 SOE 擴充仍活著」
   ——最可能的觸發是**版次改名或該服務下架**（版次寫在服務名稱裡、每兩個月換一次，
   這是真實風險）。全站斷線時只能改天再跑，或改走需登入的另一個平台。
2. **執行時的訊息也要改**。原本只印「改走 fallback」，會給虛假的安全感；
   現在同時印出「逐筆回填打的是同一台主機，全站斷線時本路徑同樣會失敗」。
3. **順手砍掉為了 fallback 而生的機械**。本例 fallback 底下掛了一整套「缺口偵測＋
   子號探測補正」（149 行），前提是「候選清單受限於快照、需要自動猜補」——
   主路徑改成範圍查詢後這個前提消失了，且走到 fallback 時本來就接受資料降級，
   **猜補只會讓人誤以為資料已經完整**。移進 legacy、保留可追溯，回歸測試留在原處。

## 下次注意

- **寫「備援」前先問一句：這兩條路的失效模式重疊多少？**
  同主機／同帳號／同金鑰／同 DNS／同一份設定檔，任何一項共用，
  那一項就是共同單點，備援對它無效。
- **文件與訊息裡的「因為 X 所以有備援」是可以被查證的**，不要只當成敘述抄下去。
  本例的說法在文件裡躺了兩週，查一次位址就推翻了。
- 沒有真備援不一定要補一條——**講清楚沒有，比假裝有更有用**。
  操作的人知道「這時候只能改天再跑」，就不會浪費時間對著失敗的 fallback 除錯。
- 相關：[[初篩工具零命中不等於無涉及]]（同一族：工具「有回應」不等於「有效」）、
  [[候選清單來自舊快照是結構性盲點]]（同一次精簡查出來的另一條）。
